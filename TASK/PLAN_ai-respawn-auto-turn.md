# 任务方案：自动静音判停语音对话

## 任务事实与边界

### 表面任务

把当前浏览器端 Push-to-Talk Demo 改为不显示说话按钮、不依赖空格键的自动半双工对话：检测到用户有效说话后，连续静音 1.2 秒自动结束本轮并触发模型回复；播放完成后重新监听。

### 用户要求

- REQ-01：撤去用户可见的 PTT 按钮及按键说话交互。
- REQ-02：检测到用户说话后，连续 1.2 秒无声即判定说完并让模型回复。
- REQ-03：根据引用会话保留最小 Demo 范围，不引入语义判停、全双工或数字人功能。
- REQ-04：实现后运行相关测试与构建验证。

### 约束

- C-01：继续使用现有浏览器 → 本地网关 → 豆包 WebSocket 链路，不把供应商密钥放入浏览器。
- C-02：保持 16 kHz、单声道、PCM16LE、20 ms/640-byte 输入帧契约。
- C-03：AI 思考及播放期间维持半双工，暂停用户轮次判定，避免回声造成串轮。
- C-04：只有已经确认过有效讲话后，静音超时才可以提交；初始静音不能触发空回复。
- C-05：本轮不做语义断句、插话、AEC、全双工、RAG、长期记忆、头像/嘴型或公网部署。
- C-06：默认参数为最短有效声音约 200 ms、静音超时 1200 ms、最长单轮 30 s；参数应集中定义以便调整。

### 已核实事实

- F-01：`apps/web/src/App.tsx` 当前只在 `beginTalk` 中启用 AudioWorklet，并在 `endTalk` 中发送 `ptt.commit`。
- F-02：`apps/web/public/capture-worklet.js` 当前只负责降采样和 640-byte PCM16 分帧，不计算声音能量。
- F-03：`apps/server/src/server.ts` 已实现 `ptt.start`、`ptt.commit`、播放完成和 `ready/listening/thinking/speaking` 状态转换。
- F-04：网关仅在 `listening` 状态接受二进制音频，播放完成后才回到 `ready`，适合保留为内部轮次协议。
- F-05：当前界面中心控件、鼠标/触控事件和空格键逻辑都表达 PTT 交互，需要从前端状态流中移除。
- F-06：仓库已有 TypeScript、Node test、Vite build 与音频/协议测试脚本。

### 未知项

- U-01：目标 Windows Chrome 与实际麦克风底噪下，固定能量阈值的最佳数值。
- U-02：Chrome 页面加载时自动申请麦克风与播放 AudioContext 是否需要一次用户手势。
- U-03：用户自然停顿、轻声尾音和短促咳嗽在目标设备上的误判比例。

### 暂定假设

- ASM-01：首版能量判定以 PCM16 帧 RMS/归一化幅度阈值为依据，阈值集中在判停模块而不是散落在 UI。
- ASM-02：在目标浏览器中 `getUserMedia` 授权后可以自动维持采音；若播放策略要求手势，只增加一次性错误/重试入口，不恢复 PTT 按钮。
- ASM-03：用户接受 1.2 秒带来的响应等待，以换取较少的正常停顿抢话。

### 可用输入、工具与权限

- 可用输入：引用会话、现有 TypeScript/React/AudioWorklet/网关实现、公开 fixture 与离线测试工具。
- 可用工具：工作区编辑、Node.js/npm、TypeScript 检查、Node test、Vite 构建；必要时本机 Chrome 麦克风/扬声器人工验证。
- 获批权限：修改工作区内源码、测试和文档；运行本地检查/构建；使用本机浏览器麦克风和扬声器进行验证。
- 不含权限：读取或输出密钥值、真实人物资料、公开部署、Git 提交、引入未批准外部服务。

## 关键挑战诊断

- D-01 | 当前 Demo 把“轮次结束”绑定到用户松开按钮；撤掉按钮后，如果没有一个独立且可验证的判停状态机，系统要么永远不提交，要么在初始静音、短噪声或自然停顿时错误触发。判停又必须与网关已有 listening/thinking/speaking 链路准确交接，否则会产生重复提交、丢尾音或播放期间回声串轮。

### 支持链

1. F-01 与 F-05 表明现有轮次边界完全由 PTT UI 事件驱动。
2. F-02 表明采音层尚未提供能量或声音活动信号。
3. F-03 与 F-04 表明服务端只需接收一个明确的 `ptt.commit`，但不会替浏览器决定静音何时结束。
4. U-01 至 U-03 表明阈值、自动播放和误判必须用单元测试与目标环境观察校准。

### 为何关键

如果 D-01 不先解决，删除按钮只会把“松开提交”变成一个缺失事件；UI 看似自动化，模型却不会稳定回复。把判停做成独立纯逻辑并保留网关协议，可在不改供应商适配器的情况下定位问题和回退。

### 竞争性诊断与反证

- ALT-01：主要问题只是 UI 需要换成状态动画。反证：如果没有可重复的 commit 事件，任何 UI 都无法完成一轮；只有判停单元测试和网关回路已通过后，UI 才是主要剩余问题。
- ALT-02：应直接启用供应商/语义 VAD 或改成级联语音 Agent。反证：这会引入新供应商能力和不可控的事件差异；只有固定能量判停在目标设备上持续误判，或浏览器无法可靠自动采音，才重新评估该路线。

## 指导方针

- G-01 | 以“浏览器侧可测试判停器 + 现有网关轮次协议”为核心，先建立状态和参数，再接自动采音，最后移除 UI 入口并做端到端回归；任何判停失败先回到判停层，不用增加视觉或供应商功能掩盖。
- G-02 | 保留旧 PTT 控制只作为内部会话接口；把用户操作从按钮/键盘替换为浏览器生命周期和判停事件。AI 回复期间不捕获用户轮次，播放完成后由同一状态机开启下一轮。
- AI 自主范围：可修改工作区中的前端、AudioWorklet、可复用判停模块、测试、README、架构和 TASK 记录；可运行本地检查与构建。涉及真实密钥、额外付费调用、公开部署或扩大到全双工时必须停止并询问。
- 必须询问条件：自动播放被浏览器策略阻断且需要改变“无按钮”范围时；真实设备误判需要引入新 VAD/服务商能力时；用户要求改变 1.2 秒或加入插话时。
- NG-01 | 不把“自动静音判停”扩展为语义判停、全双工或真人复活系统；这些不能直接消除 D-01，且会扩大测试变量。

## 近端目标与杠杆点

- O-01 | 在本地 Windows Chrome 中完成至少一轮稳定循环：授权麦克风 → 检测到有效讲话 → 静音 1200 ms → 自动 `ptt.commit` → 播放回复 → 自动回到监听；离线测试覆盖所有关键边界。
- 可行性：现有网关和音频格式契约已经通过上一轮闭环验证，主要新增逻辑集中在浏览器/AudioWorklet 和纯判停模块。
- 减少的未知：O-01 将分别暴露阈值误判、浏览器自动播放、状态重入和播放后重启问题，为后续是否升级 VAD 提供证据。
- L-01 | 最大杠杆是把“何时提交”从 DOM 事件中抽离成可注入时间与帧能量的纯状态机；它能用廉价合成样本覆盖大多数错误路径，再把真实麦克风只留给阈值校准。
- 集中资源方式：只建设一个判停器、一个自动轮次控制器和一个无 PTT 的状态界面；不并行改网关协议或供应商适配器。
- 杠杆失效信号：合成帧无法稳定区分初始静音/短噪声/真实讲话，或目标浏览器无法在无持续按钮的前提下自动启动/播放；此时暂停并回到 U-01/U-02，评估自适应阈值或一次性启用入口。
- 暂不追求的终局：语义句末判断、用户打断 AI、全双工、真实人物人格/脸/声音复现。

## 链式弱环节与风险

- W-01（判停事件）：输入是逐帧能量和单调时间，输出是唯一的 commit 事件；A-01/A-02 是前置闸门。短噪声、初始静音或恢复讲话处理错误都会阻断整轮。
- W-02（状态重启）：输入是网关状态和播放队列完成事件，输出是下一轮唯一监听；A-03/A-04 是前置闸门。旧计时器、旧 AudioWorklet 或 ready 重入会造成重复轮次和串轮。
- 串行关系：A-01 → A-02 → A-03 → A-04 → A-05 → A-06；A-07 依赖 A-04，A-08 必须等待 A-07。判停模块先于浏览器接入，避免真实设备掩盖逻辑错误。
- 风险 R-01（阈值误判）：环境噪声导致永不静音或轻声漏检；先用固定合成样本和集中参数验证，真实失败时暂停并评估自适应底噪/VAD。
- 风险 R-02（自动播放限制）：Chrome 可能要求一次用户手势；保留错误与一次性重试入口，不能悄悄恢复 PTT 交互。
- 风险 R-03（范围膨胀）：语义判停、插话和全双工会重新定义状态机；任何此类请求都必须暂停并新建方案版本。

## 假设与失败信号

- H-01 | 固定能量阈值加 200 ms 最短讲话时长能在目标近讲环境中区分讲话与短促噪声。预期观察：合成帧测试全部通过，人工一轮不会因初始静音或轻微噪声自动提交。最小验证：A-01/A-07 的合成帧与一轮本机观察。通过标准：初始静音和短促噪声均不产生 commit，正常讲话能进入有效讲话。失败信号：短噪声产生 commit、正常讲话未进入有效讲话或电视/风扇使 30 s 上限频繁触发。失败后重查阈值层和 U-01，不先改网关。
- H-02 | 网关现有 `ready → listening → thinking → speaking → ready` 状态足以承载自动轮次。预期观察：每轮只出现一个 start/commit，播放完成后恰有一个新轮次。最小验证：A-04/A-07 的状态测试与一轮浏览器验证。通过标准：状态测试无重复 start/commit，播放完成后只创建一个新轮次。失败信号：重复 start、播放期间 commit 或旧计时器越过轮次。失败后重查状态控制和清理层。
- H-03 | 移除可见按钮不会让目标浏览器无法完成麦克风/播放初始化。预期观察：授权后页面自动进入监听，若策略阻断则出现明确一次性错误/重试。最小验证：A-03/A-08。通过标准：授权后能进入 listening，阻断时错误信息可见且可恢复。失败信号：只有点击 PTT 才能启动，或无反馈地停在 suspended。失败后重查浏览器初始化策略，必要时提出新范围决策。
