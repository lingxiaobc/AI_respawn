# 任务方案：AI 复活 Push-to-Talk 实时语音 Demo

## 任务事实与边界

### 表面任务

根据引用对话《AI复活技术路线分析》，为当前空仓库规划一个可落地的最小 Demo：用户按住按钮讲话时持续上传音频流，松开时显式结束本轮输入，豆包端到端实时语音模型流式返回音频，客户端收到首个可播放音频块后立即播放。

### 用户要求

- REQ-01:生成一份规划文件，而不是立即实现 demo。
- REQ-02:规划应以引用对话已经收敛的技术路线为依据。
- REQ-03:当前先验证“按住说话 → 模型返回语音 → 立即播放”的完整链路。
- REQ-04:当前不做声音复刻；数字人视频、真实人物脸部驱动也不进入本轮最小闭环。
- REQ-05:规划需能指导后续编码、验证和失败定位，而不是只有里程碑名称。

### 约束

- C-01:真实火山引擎密钥不得出现在浏览器代码、日志、提交记录或规划文件中；仓库必须先有 `.gitignore` 和 `.env.example`，再允许创建本地 `.env`。
- C-02:服务协议、鉴权头、资源 ID、事件号、音频格式与模型版本必须以执行当日的官方文档和控制台实际开通项为准，不把引用对话中的示例值直接写死。
- C-03:本轮只做单用户、半双工 Push-to-Talk；AI 播放期间麦克风关闭或忽略输入。
- C-04:先验证固定 PCM 样本的服务端闭环，再接本机音频设备，再接浏览器；不得跳过上游闸门直接堆 UI。
- C-05:当前仓库没有遗留兼容负担，但外部模型 API 和控制台凭据形态处于变化中，协议适配必须封装在独立 provider adapter 内。
- C-06:开发与验证默认只在本机进行，不含公网部署、账号系统、多人并发或客户数据接入。
- C-07:原始用户音频默认只在内存中流转；诊断落盘必须使用人工生成/公开测试样本，真实录音需用户另行授权。

### 已核实事实

- F-01:`P:\codex_project\AI_respawn` 当前只有 `.git`，`main` 分支尚无提交，也没有 demo 代码、工程说明或既有依赖。
- F-02:本机已检测到 Node.js `v24.13.1` 与 npm `11.8.0`；npm 探测出现用户级全局目录读取警告，实施时必须通过项目本地依赖安装验证环境，而不能假定全局 npm 状态完全正常。
- F-03:引用对话将最小交互明确为半双工 Push-to-Talk：按住期间持续发送音频块，松开只发送“本轮结束”，返回音频按块连续播放。
- F-04:引用对话把核心工程风险定位在 WebSocket 会话、音频采样/编码、流式发送和连续播放，而不是密钥文件本身。
- F-05:火山引擎官方当前将豆包端到端实时语音模型定义为 Speech-to-Speech，并区分 S2S-Omni 与 S2S-Strong Character；后者面向角色扮演/情感陪伴，前者面向低延迟助手等场景。来源：https://www.volcengine.com/docs/6561/1594360?lang=zh
- F-06:火山引擎官方产品页给出的实时语音整体延迟宣传值约为 1.5 秒；它只能作为外部基准，不能代替本机链路实测。来源：https://www.volcengine.com/products/Audio-editing-and-sound-processing
- F-07:官方产品动态显示该服务持续增加音频位深、判停、人设、联网/RAG 等能力，说明执行前重新核对接口契约是必要步骤。来源：https://www.volcengine.com/docs/6561/1329505?lang=zh

### 暂定假设

- ASM-01:首个演示环境为 Windows 桌面版 Chrome 最新稳定版，普通话单人近讲麦克风。
- ASM-02:采用 TypeScript/Node.js 单仓库；浏览器端使用 React + Vite，后端使用轻量 HTTP/WebSocket 服务，协议层独立封装。
- ASM-03:第一版使用账号已开通的豆包端到端 S2S 模型；优先 S2S-SC，若未开通则用 S2S-O 验证链路，人格效果不作为本轮成败条件。
- ASM-04:暂定验收为连续 10 轮中至少 9 轮成功，松开按钮到首个可听音频的 P95 不高于 3 秒，无明显变速、爆音、长断裂或串轮；该阈值需在执行前由用户确认。
- ASM-05:不会把静态头像、字幕、RAG、长期记忆或声音复刻偷偷纳入“顺便完成”的范围。

## 关键挑战诊断

- D-01:真正阻碍 demo 成立的不是页面或密钥存放，而是尚未被本机证据验证的一条链环系统：供应商鉴权与会话事件必须正确，输入 PCM 契约必须匹配，音频块必须按时序流式传输，返回 PCM 必须被无缝排队播放。任何一环错误都可能表现为“连接成功但无声、噪声、变速、卡顿或串轮”，如果一开始直接集成浏览器、后端和模型，将无法快速判断故障层。

### 支持链

1. F-01 表明没有既有代码或已通过的接口契约可复用。
2. F-03 与 F-04 表明目标是流式会话与实时音频，而不是一次 HTTP 请求或上传整段录音。
3. U-01、U-02 表明最上游的账号/协议仍未验证；U-03 表明浏览器采样率与设备差异会继续引入变量。
4. 因此首轮应先减少变量，建立固定样本的协议证据，再逐层增加本机设备和浏览器。

### 为何关键

如果 D-01 不被拆层，团队可能在 UI、人物形象或 Prompt 上投入大量工作，却仍无法证明核心语音闭环可用；反之，只要固定样本、设备端和浏览器端依次过门，后续数字人只是消费已验证的输出音频，而不是继续猜测基础链路。

### 竞争性诊断与反证

- ALT-01 | 问题主要是“缺一个漂亮网页”。反证：即使页面完成，只要固定 PCM 不能通过供应商会话得到有效回复，最终仍完全不可用。只有现成官方示例已在同账号、同协议、同音频参数下稳定运行，ALT-01 才会上升为主诊断。
- ALT-02 | 问题主要是“应改用 ASR → LLM → TTS 级联”。级联的调试可观测性更强，但引入三个服务、更多状态与累计延迟；除非端到端 S2S 无法开通、人格/RAG 控制无法满足或其协议在 Gate 1 失败，当前不选它作为首案。

## 指导方针

- G-01 | 采用“风险先行的纵向切片”：每阶段只新增一个主要变量，按官方契约预检 → 固定音频协议回环 → 本机 PTT → 浏览器/后端闭环 → 稳定性验收推进；上游门失败时停止，不以开发下游功能掩盖失败。
- G-02 | 按能力边界分工。用户负责人提供账号开通、密钥、成本授权和主观听感验收；AI/开发工具负责可审计的代码、测试、日志与指标；豆包负责语音理解和语音生成；浏览器只持有短期会话连接和音频状态，永不持有长期供应商密钥。
- G-03 | 把供应商变化隔离在 `provider/doubao` 适配器内，以执行当日官方文档和一次真实握手为事实源；任何协议样例都先经过最小探针验证，再被 Web 层复用。
- 优先级：可鉴权的协议闭环 > 正确音频格式 > 连续播放 > 可测延迟 > 页面观感。
- 冲突取舍：若“更像真人”与“更容易诊断”冲突，第一版选择更容易诊断；若“更低延迟”与“稳定无断音”冲突，先保证稳定，再优化首包。
- AI 自主范围：获批后可在工作区创建代码、测试、文档和不含秘密的配置样例；可运行本地测试。涉及付费调用、真实密钥、真实人物资料、公开部署或范围扩大时必须询问。
- NG-01 | 不把“做出 AI 复活”当作本轮目标；本轮只证明可复用的实时语音闭环。
- NG-02 | 不实现声音复刻、数字人脸部/嘴型、RAG、长期记忆、情绪表情、全双工插话、VAD 自动判停、微信/小程序、移动端或多人并发，因为它们会增加变量但不能消除 D-01。
- NG-03 | 不为了复用未来架构而先引入 LiveKit、RTC 房间或多服务微服务；只有最小 WebSocket 网关达到瓶颈并有测量证据后才升级基础设施。

## 近端目标与杠杆点

- O-01:在本机 Chrome 上得到一个可重复验证的单用户 Push-to-Talk demo：按下后持续发送音频，松开后模型返回流式音频并立即连续播放；连续 10 轮达到 ASM-04 的暂定成功/延迟/听感标准，同时保留不含秘密的分层指标与复现步骤。
- 可行性：官方提供端到端 S2S 产品，引用对话已经收敛交互模型；现有 Node.js、Web Audio API 与 WebSocket 足以实现客户端和网关。尚未拥有的供应商访问权被放在 Gate 0，而不是假定已经具备。
- 减少的未知：O-01 会同时回答账号/协议能否接通、音频参数是否兼容、浏览器采集与返回播放是否稳定、半双工延迟是否可接受，并为后续 Avatar 层提供稳定音频接口。
- L-01 | 最大杠杆是先用“格式已知的固定 PCM/WAV”穿透真实供应商协议。它去掉麦克风、浏览器重采样和播放设备三类变量；一旦该测试通过，剩余问题就可以被限定在设备或 Web 音频层。
- 集中资源方式：第一轮只建设一个 provider adapter、一个音频契约和一个会话状态机；不并行建设 Avatar、人格库或部署体系。
- 杠杆失效信号：官方不提供当前账号可用的直接 S2S 接口；固定样本在正确开通和契约下仍无法得到有效音频；或 S2S 返回无法满足基础人格/控制需求。出现任一信号时，回到 ALT-02 比较级联路线，而不是继续扩展 UI。
- 暂不追求的终局：具体逝者的脸、声音、人格与记忆复现，以及像真人视频通话的全双工体验。

## 链式弱环节与风险

- W-01: （供应商协议与会话）输入是用户真实开通信息和执行日官方契约，输出是能稳定返回有效音频的 adapter。负责人是实施者，用户负责账号/成本授权。Gate 0 要求 A-01/A-02 完成；Gate 1 要求 A-03 连续 3 次通过。任何鉴权、事件顺序或会话清理失败都会阻断 A-04 及之后工作。
- W-02: （端到端音频契约与连续性）输入是每层明确的采样率、位深、声道、帧长与时钟，输出是听感正常且可测的采集/发送/播放链。Gate 2 要求 A-04/A-05 本机连续 5 轮通过；Gate 3 要求 A-06/A-07/A-08 浏览器闭环通过；Gate 4 才运行 A-09/A-10。
- 风险 R-01：凭据泄漏。进入闸门为 `.gitignore` 先于 `.env`；日志集中脱敏；发现泄漏立即停止、轮换凭据、清理历史并重查 C-01。
- 风险 R-02：音频参数表面匹配但时钟漂移或块边界错误。用固定 fixture、离线 WAV 与每层样本计数交叉验证；失败回到 A-02 音频契约或 A-07 调度层。
- 风险 R-03：供应商宣传延迟与本机实际不同。以按钮松开、上游首包、浏览器首声三个时间点分别测量；失败时先定位网络/模型/播放层，再决定是否放宽阈值或评估 RTC/级联替代。
- 风险 R-04：范围膨胀。任何 Avatar、声音复刻、RAG、全双工或部署请求都触发计划改版，不得塞入当前验收。
- 串并行理由：A-01 至 A-05 严格串行，因为后一步依赖前一步产出的真实契约；A-06 网关与 A-07 浏览器虽然模块上可分，但首版仍按接口先后推进以避免双向漂移；A-09 中的离线测试可在对应模块完成后增量编写，但 Gate 4 统一验收。
- 中止条件：Gate 0 无可用服务/凭据；Gate 1 固定样本无法返回有效音频；秘密无法隔离；音频数据或会话状态无法可靠归因；用户拒绝调用成本或麦克风权限。中止后分别从输入/权限、D-01/G-03、A-06、A-02/W-02 或 Q-01 层返工。

## 假设与失败信号

- H-01 | 当前账号可通过官方直连 S2S WebSocket 契约完成半双工 PTT。预期观察：固定 PCM 结束后收到合法、可播放的语音块；最小验证：A-03 连续 3 次；通过标准：三次均完成且正常关闭；失败信号：正确开通后仍持续鉴权/事件错误或无音频；失败后重查 U-01/U-02、D-01 与 G-03，并启动 ALT-02 比较。
- H-02 | 统一音频契约与分层 fixture 足以隔离大多数“无声/噪声/变速/断续”故障。预期观察：相同 fixture 在离线、本机与浏览器层的样本数、时长和频谱主特征一致；最小验证：固定正弦波加固定语音；通过标准：时长与速率无可感知偏差、无削波；失败信号：跨层样本数或播放时钟持续漂移；失败后重查 A-02 和 W-02，而不是修改模型 Prompt。
- H-03 | 半双工流式上传能在普通本机网络达到可接受的演示延迟。预期观察：10 轮中至少 9 轮完成且 P95 首声不高于暂定 3 秒；最小验证：A-10；失败信号：模型已及时返回但播放晚、供应商首包持续超阈值或断线率超过 10%；失败后按指标重查 A-05/A-06/A-07，必要时重新决定阈值或技术路线。
- H-04 | 直接 S2S 比自建 ASR → LLM → TTS 更适合作为当前最小闭环。预期观察：一个 provider adapter 即可满足对话、声音输出和基本人设，且 Gate 1-4 可通过；最小验证：完成 A-03 后评估控制能力与首包；通过标准：无需新增外部服务即可继续；失败信号：S2S 无法获得、人设/内容控制不可接受或调试不可观测性阻塞；失败后回到 ALT-02，比较级联路线的延迟、成本与可控性。
- 异常处理：所有异常先记录为事实或未知，按鉴权、协议、输入音频、模型返回、网络转发、播放调度、UI 状态分类；不得把不利结果简单标为“网络波动”或无限重试。
