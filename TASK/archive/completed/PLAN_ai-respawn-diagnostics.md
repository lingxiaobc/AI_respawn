# 任务方案：最小日志与诊断系统

## 任务事实与边界

### 表面任务

为本地 AI Respawn PTT Demo 增加可留存、可关联、可复盘的最小诊断日志系统，服务后续故障排查；明确不保存输入音频、输出音频、转写文本、模型回复、Base64 或密钥。

### 用户要求

- REQ-01：增加日志和诊断系统，为后续故障排查做准备。
- REQ-02：采用已确认的最小内容，不记录输入/输出音频内容。
- REQ-03：日志应能定位连接、会话、轮次、供应商、网关和浏览器错误发生在哪一层。
- REQ-04：日志能够在进程结束后保留，并提供查看或导出方式。
- REQ-05：显示简短诊断 ID，便于用户反馈问题。

### 约束

- C-01：只记录元数据、事件、关键耗时、结构计数、错误上下文和供应商排查 ID；不得记录音频、文本、Base64、API Key 或完整请求/响应。
- C-02：日志只写本机被 Git 忽略的 `logs/` 目录，不上传外部服务，不改变现有单用户 localhost 范围。
- C-03：默认按日期分 JSONL 文件并保留最近 7 天；清理失败不得阻断语音会话。
- C-04：日志写入失败不得让主链路崩溃；应退回控制台并保留诊断 ID。
- C-05：不删除现有固定样本探针验证能力；本任务不新增真实模型调用。
- C-06：不引入远程监控、告警平台、完整可观测性面板或多用户日志隔离。

### 已核实事实

- F-01：`scripts/probe.ts` 会把脱敏供应商事件摘要写到 stdout，并输出固定样本 WAV，但不会持久化事件日志。
- F-02：`scripts/ptt.ts` 会把每轮摘要和错误写到 stdout，进程结束后没有结构化记录。
- F-03：`apps/server/src/server.ts` 当前只打印 `gateway-ready`；会话、状态、轮次、错误和关闭原因没有服务端持久化记录。
- F-04：`apps/web/src/App.tsx` 只在页面内保存轮次、延迟、输入帧数和错误，刷新页面即丢失。
- F-05：`safeEventSummary` 已避免输出完整事件正文和 Base64，但没有统一的日志 schema、会话 ID 或文件写入器。
- F-06：`docs/architecture.md` 已列出期望的时间点、事件 ID、Logid 和指标，但代码只实现了其中一部分。
- F-07：`.env` 与 `artifacts/` 已被 Git 忽略；`logs/` 尚未加入忽略规则。

### 未知项

- U-01：单个供应商连接是否始终能取得 `X-Tt-Logid`；现有代码只在握手拒绝时从响应头提取它。
- U-02：浏览器能否在 WebSocket 已进入关闭流程后可靠上报客户端错误。
- U-03：按日期滚动和 7 天清理在 Windows 文件占用下的具体失败形态。

### 暂定假设

- ASM-01：生命周期事件、状态、耗时、计数和错误上下文足以区分主要故障层，无需保存内容。
- ASM-02：单进程本地网关追加 JSONL 足以满足当前单用户场景，不需要数据库或外部日志服务。
- ASM-03：会话 ID、轮次号、供应商 event_id/Logid 能将网关、provider、CLI 和浏览器的记录关联起来。
- ASM-04：日志文件路径与简短诊断 ID足以让用户在没有终端面板时提交排查信息。

### 可用输入、工具与权限

- 可用输入：当前 TypeScript/Vite 工程、已有协议/音频测试、现有 stdout 日志行为、用户已批准的最小字段清单。
- 可用工具：工作区编辑、Node.js 测试/类型检查/构建、本地服务和浏览器验证。
- 已批准权限：写入工作区和本地 `logs/` 目录、修改 `.gitignore`、运行本地检查和故障测试。
- 明确禁止：读取或打印密钥值、保存音频或文本、远程上传日志、公开部署、扩大产品范围。

## 关键挑战诊断

- D-01：当前故障信息分散在临时 stdout、浏览器内存和少量错误转发中，缺少持久化记录与跨层关联 ID；因此即使不保存音频内容，也无法稳定判断故障发生在浏览器、网关、供应商协议还是关闭/播放阶段。

### 支持链

1. F-01/F-02 说明已有日志只能在命令运行时观察，无法在事后查询。
2. F-03/F-04 说明网关和浏览器没有同一条会话/轮次记录。
3. F-05/F-06 说明已有脱敏摘要和指标设计可以复用，但缺少统一落盘和关联实现。
4. 用户明确不需要音频/文本，排除了以保存内容换取可观察性的高噪声路线。

### 为何关键

诊断系统的最弱环节是“记录能否把一次失败完整串起来”，不是“记录多少内容”。如果先记录原始 payload，会增加隐私和噪声，却仍不能说明哪一层先失败；必须先建立统一的最小事件链。

### 竞争性诊断与反证

- ALT-01：保存完整 provider 事件、请求响应和音频样本，以便事后重放。若最小元数据无法区分某类故障，才考虑针对性增加脱敏字段；否则该路线的存储、隐私和解析成本超过收益。
- ALT-02：只保存结构化生命周期元数据、关键计数、耗时、错误和关联 ID。若成功/失败注入测试仍无法定位责任层，再补充单个缺失字段；当前选择此路线。
- 选择：先实现 ALT-02，并用成功、超时、拒权、上游错误、浏览器关闭和播放中断验证其诊断覆盖；不以“日志越多越好”作为通过标准。

## 指导方针

- G-01：以一个共享、可测试、可脱敏的 JSONL logger 为唯一落盘边界；所有层只提交结构化元数据，不直接拼接日志文件。
- G-02：以“会话开始/轮次开始/轮次完成/错误/会话关闭”五类事件为主，逐音频分片只累计计数，不逐条落盘。
- G-03：所有记录必须可用 `session_id + round` 串联，供应商 event_id/Logid 只作为排查索引，不记录完整请求或响应。
- G-04：日志故障不能反向破坏语音主链路；写入失败降级到 stderr，并继续执行已有状态清理。
- NG-01：不保存输入音频、输出音频、转写正文、模型正文、Base64、API Key 或完整原始事件。
- NG-02：不把日志系统扩展成远程监控、指标平台、告警、用户账户或多租户审计系统。
- NG-03：不同时维护 gateway、browser、probe、PTT 四套互不兼容的日志格式。

## 近端目标与杠杆点

- O-01：任意一次成功或失败的浏览器轮次都能在本地 JSONL 中找到一组可解析、可关联、无敏感内容的记录，并能通过简短诊断 ID定位该会话。
- 可行性：当前各层已经产生状态、错误、轮次和耗时信号，只需统一 schema、ID 和写入边界，不需要真实模型调用或音频存储。
- L-01：网关 logger 与 session/round ID 是最大杠杆，能把 provider、browser、CLI 的局部信号接到同一条记录链。
- L-02：故障注入和日志扫描测试是低成本验证，可在不保存音频和文本的前提下证明诊断能力与隐私边界。
- 杠杆失效信号：成功/失败记录无法通过 ID 关联、错误只剩“连接失败”而无法定位阶段，或日志写入异常导致主链路失败；此时回到 schema/接口层，不增加原始内容。
- 暂不追求：远程集中日志、实时告警、完整性能监控、自动故障修复和多用户审计。

## 链式弱环节与风险

- W-01（日志写入边界）：输入是结构化事件，输出是本地 JSONL。闸门是写入失败不得影响主链路；失败回到 A-02/A-09。
- W-02（跨层关联）：输入是各层局部信号，输出是同一 session_id/round 下的可追溯记录。闸门是成功和失败路径均能串联；失败回到 A-03/A-05。
- W-03（浏览器上报）：输入是浏览器短错误/关闭信息，输出是网关可保存的安全元数据。闸门是断线时仍有网关 close 兜底；失败回到 A-06，不缓存原始内容。
- R-01（隐私）：任何日志出现音频、文本、Base64 或密钥即阻断交付，删除测试产物并回到 A-01/A-09。
- R-02（日志膨胀）：逐 delta 记录或无滚动导致文件快速增长时，停止扩展字段，改为计数/摘要并回到 G-02。
- R-03（诊断反噬主链路）：logger 抛错、文件锁或权限错误导致会话失败时，立即启用 stderr 降级并回到 A-02。
- 串行关系：A-01→A-02→A-03→A-04→A-05；A-06 依赖 A-03/A-05；A-07 与 A-08 依赖已接入的日志接口；A-09 等待实现稳定；A-10 等待 A-08/A-09。

## 假设与失败信号

- H-01：主张：五类生命周期事件、关联 ID、关键耗时/计数和错误上下文足以定位当前主要故障层。预期：成功和四类失败注入都能指向 browser/gateway/provider/close 中至少一层；最小验证：A-09/A-10；通过标准：每个场景都能按 ID找到责任层；失败信号：只能得到无阶段的通用错误；失败后重查 A-01 schema，而不是保存原始内容。
