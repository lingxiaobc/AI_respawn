# 任务方案：修复实时语音尖刺杂音

## 任务事实与边界

### 表面任务

根据用户实际听感和已有测试产物，修复豆包实时语音 Demo 的尖刺杂音，并重新验证“按住说话 → 模型理解 → 正常人声播放”的闭环。

### 用户要求

- REQ-01：基于已收集的日志、音频产物和用户反馈进行优化。
- REQ-02：保留当前单用户、半双工 Push-to-Talk 范围，不引入声音复刻、Avatar、RAG 或部署。
- REQ-03：使用现有根目录 `.env` 做一次最小真实模型复测，不输出密钥。
- REQ-04：修正错误的音频验收结论，并补充可复现的格式回归测试。
- REQ-05：在修复前不再把“收到字节”或“写入扬声器”当作正常人声通过条件。

### 约束

- C-01：密钥只能由后端从未跟踪的 `.env` 读取；不得进入浏览器、日志、测试快照、方案或 Git。
- C-02：模型会话、麦克风输入、浏览器状态机和半双工行为保持不变，除非音频格式修复必需。
- C-03：所有下游播放端只接受统一的 24 kHz、单声道、PCM16LE 契约。
- C-04：真实模型调用限一次最小固定样本探针；调用结果必须先过离线波形检查，再进入人工听感验收。
- C-05：不得用启发式静默猜测替代显式格式契约；不确定时停止播放并保留原始证据。
- C-06：本轮不提交 Git；提交需要用户另行提出或批准。

### 已核实事实

- F-01：三次直连均收到 `response.output_audio.delta`，输出分别约 382584、482072、382480 bytes；会话事件和关闭流程完整。
- F-02：本地 PTT 五轮均采到非静音输入且 ASR 完成，说明密钥、输入设备和基本模型链路不是当前主要故障。
- F-03：返回 WAV 的 16-bit 解析在有声段呈现 `[15126, 0, 15132, 0, ...]`；每四字节按 Float32LE 解析得到有限、连续且合理的波形值。
- F-04：当前 `session.create` 只声明 PCM 类型和采样率；CLI、网关、浏览器和 WAV 封装均强制按 Int16/16-bit 处理。
- F-05：用户实际听到全是尖刺杂音，否定了此前仅凭非空字节、队列写入和结构合法 WAV 得出的“输出通过”。
- F-06：问题同时覆盖 CLI 与浏览器共享的输出解释边界，不能归因于单个扬声器或页面控件。
- F-07：现有 v1 代码、测试和首次提交保留，便于回退和比较；本轮只做格式边界修复及其验收。

### 未知项

- U-01：执行日官方接口是否存在可稳定强制 PCM16LE 的精确字段名。
- U-02：所有真实 `delta` 分片是否始终在 Float32LE 样本边界上结束。
- U-03：修复后的真实浏览器输出是否在用户设备上达到“正常人声”主观标准。

### 暂定假设

- ASM-01：当前真实返回主体是 Float32LE PCM；该假设可由一次最小真实探针证伪。
- ASM-02：在 provider adapter 建立唯一的 Float32LE→PCM16LE 流式转换边界，可以同时修复探针、CLI、网关和浏览器。
- ASM-03：转换后的 24 kHz PCM16 可继续复用既有播放队列和 Web Audio 调度，无需改动会话状态机。
- ASM-04：修复后的浏览器人工验收采用 5 轮，要求无尖刺、变速、重叠、长断裂或明显截断。

### 可用输入、工具与权限

- 可用输入：现有 `artifacts/` 返回样本、provider 事件日志、当前 TypeScript/Vite 工程、用户已填入的 `.env`。
- 可用工具：工作区文件编辑、Node.js 类型检查/测试/构建、一次真实固定样本探针、本地浏览器和音频设备。
- 已批准权限：写入工作区、读取非秘密配置、使用一次真实模型调用、重启本地 Demo、请求用户完成浏览器听感确认。
- 明确禁止：打印或读取密钥值、公开部署、接入真实逝者资料、扩大到 Avatar/声音复刻/RAG、未验证格式的播放。

## 关键挑战诊断

- D-01：模型输出事件已到达，但服务端音频编码/位深与客户端 PCM16 假设不一致；当前链路把一个真实样本拆成两个 Int16 值，制造交替零值和尖峰，因此“协议成功”没有转化为“可听人声”。

### 支持链

1. F-01/F-02 排除了“没有返回”以及“麦克风完全失效”。
2. F-03 以同一份 payload 的两种解释产生强对比：Int16 结构异常，Float32LE 数值连续。
3. F-04 说明格式假设在 provider、CLI、网关和浏览器之间被重复硬编码，任何一处修补都会留下漂移风险。
4. F-05 是最终用户听感反证，因此必须撤销旧 Gate 结论并把听感纳入验收。

### 为何关键

输出播放是链环的下游最弱环节；继续优化 UI、延迟或 Prompt 不会改善错误解码。只有先建立可信的 PCM16 边界，后续设备和浏览器测试才有意义。

### 竞争性诊断与反证

- ALT-01：问题是供应商请求没有明确 PCM16，服务端选择了其他编码。若补充官方确认的 PCM16 字段后，一次探针直接返回 2-byte 对齐且 Int16 波形正常，则应优先采用显式协商并取消转换。
- ALT-02：服务端已经返回有效 Float32LE，问题只在本地解码。若原始 payload 在 Float32LE 解释下持续满足 4-byte 对齐、有限值和连续波形，而显式协商字段不可用或无效，则采用 provider 内部流式转换；当前首选此路线。
- 选择：先用离线样本和一次真实探针区分 ALT-01/ALT-02；无论哪条成立，下游都只消费统一 PCM16，不允许把未知格式传给播放器。

## 指导方针

- G-01：以“单一 provider 音频规范化边界”为修复中心，先修格式再修播放，不改已工作的输入和会话状态机。
- G-02：每一步只引入一个主要变量；保留旧原始样本、显式源格式和可回退路径，供应商格式不确定时停止而不是猜测。
- G-03：验收必须同时包含事件证据、字节/波形证据和人工听感；任一缺失都只能标记待验收。
- 优先级：可听正常人声 > 格式契约可追溯 > 播放连续性 > 延迟指标 > 页面观感。
- NG-01：不把“有 `delta`/有 WAV/有扬声器写入”当作人声通过。
- NG-02：不把修复扩展为换模型、级联 ASR/LLM/TTS、Avatar、声音复刻、RAG 或部署。
- NG-03：不在 provider 之外增加多个格式猜测器；失败时保留原始数据并回到契约确认层。

## 近端目标与杠杆点

- O-01：在一次最小真实探针内产出可验证的 24 kHz 单声道 PCM16LE 音频，并使共享的 CLI/网关/浏览器链路只消费该规范；随后完成 5 轮浏览器主观听感确认。
- 可行性：原始返回数据已存在，转换是局部、可逆、可用纯函数测试的变化；既有会话和输入链路无需重建。
- L-01：唯一规范化边界是最大杠杆，能一次影响三个下游消费者，避免逐端打补丁。
- L-02：旧尖刺样本与合成 Float32 fixture 是低成本回归杠杆，可在不调用模型时证明“旧路径失败、新路径正确”。
- 杠杆失效信号：Float32LE 不满足有限值/对齐/波形约束，或真实探针返回与离线样本不同；此时停止播放，回到 U-01 的官方字段核验或 ALT-01。
- 暂不追求：10 轮完整商业验收、Avatar、声音复刻、长期记忆、公开部署和全双工打断。

## 链式弱环节与风险

- W-01（provider 输出格式）：输入是未带充分元数据的 Base64 delta，输出是明确的 PCM16LE。Gate：A-03 需通过对齐/有限值/尾部检查；失败回到 A-02/A-07 的契约核验。
- W-02（共享音频边界）：输入是规范化 PCM16，输出是 CLI、网关、浏览器都一致的字节流。Gate：A-04/A-05/A-08 需通过；任一消费者直接解释原始 delta 即阻断。
- W-03（最终听感）：输入是可解析 WAV 和浏览器播放，输出是用户确认的正常人声。Gate：A-09 需 5 轮通过；无法自动确认时暂停，不用结构指标替代。
- R-01（凭据）：真实调用只允许一次，密钥值不落盘；发现泄漏立即停止并要求轮换。
- R-02（供应商变化）：如果一次探针与历史样本格式不同，保留原始数据、停止播放、回到 U-01/ALT-01；不扩大到自动兼容。
- R-03（过早恢复）：即便测试和 WAV 结构通过，用户仍听到噪音则 Gate 保持失败，重查 A-03/A-04，而不是放宽听感标准。
- 串行关系：A-01→A-02→A-03→A-04/A-05→A-06→A-07→A-08→A-09→A-10；A-04 与 A-05 共享 A-03 后可并行，但 A-06 必须等待两者均通过。

## 假设与失败信号

- H-01：主张：真实 delta 是 Float32LE。预期：每 4 字节解释得到有限值，转换后输出约为原始字节的一半且无交替零值；最小验证：A-07 一次固定样本；通过标准：样本满足 4-byte 对齐、有限值和连续波形；失败信号：4-byte 不对齐、非有限值占比异常或 Int16 直读反而正常；失败后重查 A-02/U-01 并比较 ALT-01。
- H-02：主张：单一 adapter 规范化能修复所有播放端。预期：A-04 后 CLI、网关、浏览器收到相同 PCM16 语义；最小验证：A-05 与 A-08 固定流；失败信号：任一消费者仍需特殊分支；失败后回到 A-04 接口设计。
