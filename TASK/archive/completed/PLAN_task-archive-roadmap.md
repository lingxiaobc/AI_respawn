# 任务方案：TASK 清理归档与项目总计划优化

## 任务事实与边界

### 表面任务

检查 `TASK/` 中所有计划和任务明细，按真实状态清理归档，并优化根目录 `AI_RESPAWN_DEMO_PLAN.md`，使项目只保留当前活动主线。

### 用户要求

- REQ-01 |检查所有 `TASK/PLAN_*.md` 与 `TASK/TASK_*.md`，区分完成、进行中、暂停和被替代的记录。
- REQ-02 |已完成记录放入统一文件夹；历史记录不能被删除或丢失。
- REQ-03 |用户已确认 Live2D 前置准备和技能文件已完成；尚未开始的是 Live2D 资源与前端结合。

- C-01 |只移动、复制和编辑任务/计划文档；不删除模型、PSD、源图、技能资产或日志。

- C-05 |根计划重写前必须保存旧版副本；不得改变现有代码、资产、模型或前端实现。
- C-06 |不提交、不推送、不发布；本计划只处理工作区文档结构和可追溯性。

## 关键挑战诊断

- D-01 |任务文档的状态、历史版本和用户最终事实分散在多个文件中；如果直接按文件名或旧勾选移动，会把暂停/活动路线混入完成归档，或让旧根计划继续成为错误入口。关键不是“减少文件数”，而是建立单一活动入口、可回退归档和有证据的 Live2D 完成里程碑。

### 支持链

1. F-01/F-02/F-03 显示同时存在已完成、活动和暂停任务。
2. F-04/F-06 显示旧 v1 方案和根计划仍会重复描述已被 v2 取代的路线。
3. F-05/F-07 与用户确认共同表明 Live2D 前置资源已经完成，真正未开始的是前端接入。
4. 因此必须先分类和保存，再移动归档，最后重写根计划；任何一步缺证据都不能宣布清理完成。

### 为何关键

归档动作会改变后续查找路径。没有索引和旧版备份，清理会变成信息丢失；没有把 Live2D 前置和前端接入分开，根计划会继续诱导重复制作底图和 Cubism 资源。

### 竞争性诊断与反证

- ALT-01 |按 `execution_status` 机械移动即可。反证：Live2D 旧 tracker 的状态落后于用户最终确认，机械规则会把已完成前置误留在活动区；只有所有状态与证据一致时才可采用。
- ALT-02 |只优化根计划、不移动 TASK 文件即可。反证：8 对计划/任务仍会产生多个入口和重复版本；只有外部流程强依赖原路径且无法建立索引时才考虑只做根计划迁移。
- 选择：采用“证据分类＋双层归档＋根计划重写＋验证”的组合，保留 ALT-01/02 作为失败时的降级路径。

## 近端目标与杠杆点

- O-01 |`TASK/` 根目录只保留当前活动任务；完成归档、替代归档和索引能一眼说明每份记录的状态与去向。
- O-02 |根计划准确表达“语音 v2 连续性验收仍在进行；Live2D 前置资源已完成；下一步是 Live2D 与前端结合”。
- O-03 |所有历史计划仍可通过归档索引、旧根计划副本和 Git 差异恢复。

- L-02 |用归档索引和根计划的活动队列作为唯一导航，减少重复阅读和返工。
- 杠杆失效信号：同一主题仍有两个活动入口、归档后链接失效、或用户确认与文件记录无法对应；出现即停止重写，回到 A-01/A-02。

## 链式弱环节与风险

- W-01 |Live2D 旧 tracker 的细项状态与用户最终确认不一致。进入闸门为用户确认和最终 `.cmo3`/技能包存在；阻断阈值是无法给出完成摘要或发现资源缺失。失败回到 A-01/A-03，归档为替代而非完成。
- W-02 |移动文件后根计划和索引可能断链。进入闸门为备份先行、源/目标清单和相对链接检查；失败时停止移动或恢复旧根计划。
- W-03 |v1/v2 同 plan_id 会造成错误入口。进入闸门为活动根目录只保留 v2；失败时保留兼容说明并回到 A-04。
- 风险 R-01：误移动或覆盖用户文档。缓解：只操作明确列出的 Markdown，移动前复制备份，禁止删除。
- 风险 R-02：把前端未开始误写成 Live2D 全部完成。缓解：根计划把资源准备与前端接入分成两个独立里程碑，并链接活动 `TASK_live2d-portrait-animation.md`。
- 风险 R-03：根计划重写时丢失旧 v1 的协议/验收信息。缓解：旧根计划副本进入替代归档，当前根计划只引用而不抹除历史。
- 串并行理由：A-01→A-02→A-03/A-04→A-05→A-06 严格串行；分类和备份是移动的前置门，根计划必须在最终去向确定后重写。
- 中止条件：目标归档已存在且内容不一致、活动文件依赖无法修复、用户确认与资源事实冲突、或任何动作需要删除/修改资产。中止后保留现状，回到相应证据层。
